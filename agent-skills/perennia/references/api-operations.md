# Perennia Agent Operations

Use `scripts/prn-code.mjs` when writing code-mode scripts that compose calls and
reduce results in the execution environment. Use `scripts/prn-agent.mjs` for raw
one-command REST calls. The raw script maps commands to the REST agent API and
emits JSON envelopes:

```json
{"ok":true,"status":200,"command":"probe","data":{}}
```

Dry runs use the same envelope shape with `status: null` and the planned request
under `data`. HTTP failures exit 1 with `ok: false`; usage/script failures exit
2 or 1 and still emit a JSON error object on stdout. Diagnostics are written to
stderr. Agent API keys are read from `PRN_AGENT_API_KEY`; do not pass secrets on
argv.

account self-service operations rather than agent-key-authenticated skill
commands.

## Query Filters

Pass query filters with repeated `--query key=value` flags:

```bash
node scripts/prn-agent.mjs list-history-sets \
  --query exerciseId=exercise-id \
  --query from=2026-06-01 \
  --query to=2026-06-30 \
  --query limit=50
```

Use `fields` on list endpoints that support projection, then use `--select` to
copy response subtrees into the envelope's `selected` object for downstream
code:

```bash
node scripts/prn-agent.mjs list-metrics \
  --query metricKey=bodyWeight \
  --query fields=id,name,canonicalKey,unit \
  --select metrics[].id
```

Use path parameters with either `--param key=value` or the shorthand flag:

```bash
node scripts/prn-agent.mjs exercise-analytics --exercise-id exercise-id
node scripts/prn-agent.mjs monitoring-activity --external-activity-id activity-id
```

Resolve an exercise by name before writing a workout when the caller has free
text instead of an Exercise id:

```bash
node scripts/prn-agent.mjs resolve-exercise --query name="Back Squat"
```

When `resolve-exercise` returns `resolution: "not_found"` or `"ambiguous"`, the
response includes a `guidance` object (`{"op": "POST /agent/exercises/batch-write",
"message": "..."}`) pointing back at `manage-exercise-catalog` so a code-mode
script can create the missing Exercise (or pick a candidate id) and retry the
original write in the same program, without a human in the loop. `guidance` is
`null` when `resolution` is `"matched"`.

Unknown flags are rejected so misspelled query flags are not silently converted
into path parameters. Use `--commands-json` to inspect the script's command map
from tests or code execution.

## Exercise Catalog Write Shape

User Library only — Platform Library rows can never be edited or archived
through this op. Categories are created-or-referenced: include a `categories`
entry with a new `id` to create one, or set an Exercise's `categoryId` to an
id already visible to the caller (created earlier in the same batch counts).
To customize a Platform exercise (mirrors the app's customize flow), set
`customizesExerciseId` to the Platform Exercise id being shadowed; this never
mutates the platform row, it creates a new User Library row. Archive (never
purge) an Exercise or Category by setting `deletedAt`; Sets that reference an
archived Exercise keep their history untouched.

```json
{
  "idempotencyKey": "stable-exercise-catalog-batch-key",
  "categories": [
    {
      "id": "category-id",
      "name": "Mobility",
      "sortOrder": 0,
      "colorHex": "#607D8B",
      "updatedAt": "2026-07-03T05:00:00.000Z",
      "deletedAt": null
    }
  ],
  "exercises": [
    {
      "id": "exercise-id",
      "name": "Couch Stretch",
      "categoryId": "category-id",
      "dimensions": ["duration"],
      "defaultLoadUnit": "kilogram",
      "loadMode": "added",
      "isUnilateral": false,
      "usesRpe": false,
      "isFavorite": false,
      "equipment": [],
      "notes": null,
      "customizesExerciseId": null,
      "updatedAt": "2026-07-03T05:00:00.000Z",
      "deletedAt": null
```

Dimensions are drawn from the curated registry (`load`, `reps`, `duration`,
`distance`); any subset is valid, including none (completion-only). An
out-of-registry dimension or an empty `name` is rejected at the request-schema
layer (`400`), not as a per-item batch error.

## Workout Template Materialize Shape

Materialize always creates a new Workout and exactly one Template Link. The
server resolves `copyPrevious` from completed history, falls back to literal
zero-values when the Exercise has never been performed, unrolls `repeat`, and
rejects expansion above 100 Sets. Use the same idempotency key for retries:
the response converges on the original server-generated ids.

```json
{
  "idempotencyKey": "stable-materialize-key",
  "workoutTemplateId": "template-id",
  "routineId": "routine-id",
  "slot": 1,
  "startedAt": "2026-07-24T05:00:00.000Z",
  "timezone": "Australia/Brisbane"
}
```

For a bare Template, set `routineId` and `slot` to `null`. For a cadence-less
Routine collection, provide `routineId` with `slot: null`. A cadenced
Routine/slot must contain an active Routine Entry referencing the Template.

## Food Library Reads and Writes

`list-foods` (`GET /agent/foods`) searches or lists the caller's own Food
library (User Foods and Recipes) with `search`/`includeArchived`/`limit`/
`cursor`/`fields`. Platform reference data is never in this list.

`search-platform-foods` (`GET /agent/foods/platform-search`) searches the
bundled USDA Platform Food dataset — the SAME offline, CC0 catalog the app
ships — with `search`/`limit`. The response includes an
`attribution` object; surface it wherever the result is shown, mirroring the
in-app USDA courtesy attribution. Open Food Facts (branded/barcode)
is not available through this operation.

`manage-foods` (`POST /agent/foods/batch-write`) creates, edits, or archives
User Foods and Recipes. A Recipe is a Food whose `recipeIngredients` carries a
flat, pre-resolved ingredient snapshot (no nesting); `recipeServingCount` is
required alongside it and forbidden on a plain Food. Nutrient vectors are
validated by the shared two-tier nutrient validator — missing
nutrients stay `unknown`, never coerced to zero.

```json
{
  "idempotencyKey": "stable-food-batch-key",
  "foods": [
    {
      "id": "food-id",
      "name": "Banana",
      "nutrientsPer100": {
        "energy": { "status": "complete", "value": 89, "entered": "89", "unit": "kilocalorie" },
        "protein": { "status": "complete", "value": 1.1, "entered": "1.1", "unit": "gram" }
      },
      "isLiquid": false,
      "servingLabel": "medium",
      "servingSize": 118,
      "packageSize": null,
      "recipeIngredients": null,
      "recipeServingCount": null,
      "updatedAt": "2026-07-04T05:00:00.000Z",
      "deletedAt": null
    }
  ]
}
```

Once a Food exists, `log-meal` can reference it **by id alone** — omit
`name`/`nutrients`/`isLiquid`/`servingLabel`/`servingSize`/`packageSize` on the
Food Entry and the server resolves the full self-describing snapshot from the
caller's own Food (a create-then-log program in two calls, no re-entry of
nutrient facts):

```json
{
  "idempotencyKey": "stable-meal-batch-key",
  "meal": {
    "id": "meal-id",
    "mealType": "Breakfast",
    "startedAt": "2026-07-04T07:00:00.000Z",
    "endedAt": null,
    "timezone": "Australia/Brisbane",
    "localDate": "2026-07-04"
  },
  "entries": [
    {
      "id": "entry-id",
      "position": 0,
      "foodId": "food-id",
      "foodSource": "user",
      "portion": { "value": 1, "entered": "1", "unit": "serving" }
    }
  ]
}
```

Any field supplied explicitly on a reference Food entry is respected as-is;
resolution only fills in what is omitted. A `foodId` that does not resolve to
an active Food visible to the caller returns `422` with rule
`food_reference_not_found`.

## Nutrition Goal Write Shape

`nutrition-totals`/`nutrition-trends` use the caller's stored Nutrition Goals as the
default per-nutrient target when no `energyGoal`/`proteinGoal`/`carbohydrateGoal`/
`fatGoal` query param is supplied; an explicit query param still overrides the stored
Goal for that nutrient. Both responses include a `goalSource` field
(`"query"` | `"stored"` | `"none"`) reporting which source won.

```json
{
  "idempotencyKey": "stable-goal-batch-key",
  "targets": [
    {
      "id": "goal-energy-id",
      "nutrient": "energy",
      "value": 2200,
      "updatedAt": "2026-06-24T05:00:00.000Z",
      "deletedAt": null
    }
  ]
}
```

Goalable nutrients are the fixed v1 set: `energy`, `protein`, `carbohydrate`, `fat`
. Reuse a target's `id` to update it; set `deletedAt` to clear it (an
ordinary LWW tombstone, never a purge).

## Dose Write Shape

`log-doses` (`POST /agent/protocols/doses/batch-write`) logs, edits, or tombstones
Doses in one idempotent batch. Each Dose is validated by the shared two-tier dose
validator (`validate-dose`), snapshotted self-describingly, and stamped
`provenance: "agent"` server-side. A Dose is user log — `compoundId` and
`protocolId` are optional tags, never required. Every newly authored row `id` is a
client-generated UUIDv7; existing legacy ids remain valid only for edits or
archives of rows already owned by the account. Keep the `idempotencyKey` stable
across retries: the first request claims an atomic receipt, and simultaneous
retries return `duplicate` without writing or nudging again. Reusing the key with a
different payload returns `422` with rule `idempotency_key_conflict`; generate a
new key for genuinely new work.

```json
{
  "idempotencyKey": "stable-dose-batch-key",
  "doses": [
    {
      "id": "018f6a90-6d7f-7d63-bfc1-6f1025e0d010",
      "compoundId": "018f6a90-6d7f-7d63-bfc1-6f1025e0d011",
      "compoundName": "Creatine Monohydrate",
      "compoundStrength": { "value": 5, "massUnit": "gram", "perUnit": "scoop" },
      "amount": "5",
      "unit": "gram",
      "route": "oral",
      "tookAt": "2026-06-24T05:00:00.000Z",
      "timezone": "Australia/Brisbane",
      "localDate": "2026-06-24",
      "protocolId": null,
      "protocolName": null,
      "updatedAt": "2026-06-24T05:00:00.000Z",
      "deletedAt": null
    }
  ]
}
```

Set `deletedAt` to tombstone a Dose (recoverable via the Activity Log, never a
purge). Hard-validation failures return `422` with per-item `errors`/`warnings`
and no rows written.

## Effect Window Read

`effect-window` (`GET /agent/protocols/effect-window`) computes a descriptive
before/during/after summary of one outcome Metric around the logged Dose timeline
of a Compound or Protocol over a range. Provide exactly one of `compoundId` /
`protocolId` and exactly one of `metricId` / `metricKey`, plus `from` and `to`.

```bash
node scripts/prn-agent.mjs effect-window \
  --query compoundId=compound-id \
  --query metricKey=hrv \
  --query from=2026-06-01 \
  --query to=2026-06-30
```

The response returns the Dose markers plus `segments.before`/`during`/`after`,
each with `count`/`min`/`max`/`mean`. It is descriptive only (`descriptiveOnly:
true`) — never a causal, efficacy, or medical claim — and nothing it
returns is stored. A malformed request (not exactly one source/Metric,
or an unknown id) returns `422`.

## Settings Reads and Writes

`read-settings` (`GET /agent/settings`) returns the caller's **account-level**
Settings: `themePreference`, `unitSystem`, `weekStartDay`,
`defaultWeightIncrement`, `homeScreenDisplay`, `prTrackingEnabled`,
`markSetsCompleteByDefault`, `autoSelectNextSet`, plus the row's `updatedAt`
(null when the caller has never customized a field — defaults are returned).
Device-level settings (screen-on, crash reporting, auto-backup) are deliberately
**absent** from the agent surface: they describe the physical device and have no
synced row to point at.

`update-settings` (`POST /agent/settings/batch-write`) changes any subset of the
account-level fields in one idempotent Activity Log batch. Only the keys you
supply in `fields` are changed; omitted keys keep their current value. Values are
validated by the shared two-tier Settings validator — enum membership for
theme/unit/week-start/home-display, and `defaultWeightIncrement` strictly greater
than 0 and no more than 100 — so an unknown enum member or an out-of-range
increment returns `422` with no write. The write lands on the synced Settings
singleton and nudges the user's devices to pull it.

```json
{
  "idempotencyKey": "stable-settings-key",
  "fields": {
    "unitSystem": "imperial",
    "defaultWeightIncrement": 5,
    "weekStartDay": "sunday"
  }
}
```

## Activity Log Reads and Undo

`list-activity` (`GET /agent/activity`) returns a bounded, cursor-paginated
page of the caller's own Activity Log batches (accountability), each
entry carrying its batch id, actor, entity table, before/after images, and
`occurredAt`. Filter by `actor` (for example `agent`, `app`, `sync`),
`entityTable` (for example `logged_sets`, `meals`), an exact `batchId`, or an
`occurredAt` range with `from`/`to`. Internal bookkeeping rows (import
batches, monitoring-read markers) never appear here — every row is a real
user-facing write.

```bash
node scripts/prn-agent.mjs list-activity \
  --query actor=agent \
  --query entityTable=logged_sets \
  --query limit=20
```

`undo-activity-batch` (`POST /agent/activity/undo-batch`) applies a prior
batch's inverse images as a brand-new ordinary write batch — mirroring the
app's `ActivityLogRepository.undoBatch`. A create inverts to a tombstone
(archive, never a hard delete); each entry runs through its entity's own sync
push path (silent LWW, tenant isolation, its own Activity Log entry). Undo is
**batch-atomic**: if any single entry's current state no longer matches its
recorded after-image, nothing is applied, no new Activity Log batch is
recorded, and the response reports the conflicting entries with
`applied: false` and `undoBatchId: null`. Idempotent by `idempotencyKey` —
undo-of-undo resurrects the original rows.

```json
{
  "batchId": "batch-id-to-revert",
  "idempotencyKey": "stable-undo-key"
}
```
